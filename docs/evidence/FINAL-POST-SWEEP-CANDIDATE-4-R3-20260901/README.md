# Candidate #4 R3 runtime authorization and same-connection sweep binding

This first R3 packet is implementation-only. It does not claim that the managed authorization has been inserted or that the reviewed runtime has emitted fresh staging receipts. Provider execution remains blocked, the queue remains paused, and the worker remains suspended until an exact-SHA Reviewer PASS permits the bounded managed sequence.

Migration 0047 creates one Candidate #4-only runtime authorization row. Its exact job, evidence task, activation SHA, database binding, R3 task, and Founder actor are constrained. An insert trigger locks and validates the pristine active evidence authority; a second trigger rejects every update or delete. The original activation `deploy_sha` and idempotency key stay unchanged, while the provider's existing SHA gate reads the one append-only authorized runtime when present. Ordinary and legacy evidence rows continue to use their original activation SHA.

The managed authorizer runs only on the staging web service at its own exact runtime SHA, inside a serializable transaction. It locks the job and evidence row, verifies zero provider/output/publication/terminal effects and an active unexpired lease, computes the non-secret database binding on that same transaction connection, and inserts only the append-only runtime authorization. It has no queue, provider, candidate-creation, or publication path.

The PostgreSQL stale sweep now holds one checked-out connection for the database-binding query, active-job enumeration, and every stale-job transaction. Its structured receipt includes that binding. On the actual managed worker, the same interval also performs a separate read-only Candidate #4 preflight: it accepts only an active zero-effect authorization whose provider runtime equals `RENDER_GIT_COMMIT` and whose database binding equals the sweep receipt. The preflight stops before payload creation, `claimPost`, queue consumption, or any provider boundary.

After this implementation receives PASS, the bounded managed sequence is: deploy web exact SHA and apply migration; run the one authorizer; capture a fresh zero-effect readback; deploy/resume the worker at that same SHA with the queue paused; archive the structured sweep receipt containing the exact database binding and `ACCEPTED_NO_POST`; capture a fresh post-readback; suspend the worker; submit those immutable receipts for another exact-SHA review. No provider POST is part of that sequence.
